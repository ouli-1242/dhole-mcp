# Tool Deep Behavior

Tool descriptions cover parameters; this volume covers **how the tools actually behave** — tiers, limits, and the parts most likely to be misread. Value ranges still live in `tools/list`.

## web_read: the fetch chain

**Three-tier escalation**: direct HTTP (~1s) → stealthy browser when blocked or facing a JS shell → archive.org snapshot on final failure. `escalation_path` records where the call actually landed. Two no-escalation exceptions: 500/502 go to archive fallback or an honest error instead of the browser; data documents (XML / images / PDF) are never sent to the browser. On strongly anti-bot sites, send subsequent calls with `force_fetcher='stealthy'` and skip re-walking the chain. **The archive tier costs 10-30s, and no parameter disables it** — it is the last answer, not an opt-in.

**Shell-page judgment**: `content_ok` no longer means only "2xx + non-empty" — it now reads what the body actually holds. `substance` is that verdict (`ok` / `nav_only` = line-by-line menu fragments, or a page whose ENTIRE visible text is under 200 characters / `collapsed` = the words are in the HTML and dhole's reader lost them / `no_words` = a packed payload), and `substance_basis` carries the numbers it was made from so you can audit it instead of trusting it. **An absent `substance` is not `ok`**: absent means no judgment applies (PDF/JSON/image, a response that was never served as a page — a 2-byte API ack with no `Content-Type` reads identically to an empty shell, so nothing is claimed about "this page" without that evidence — a HEAD probe, a 304, or a row whose `error` already explains it). `visible_text_chars` is the page's own visible character count — the control number that separates the two failures that used to look identical: tiny body + tiny page total means the site gave you a shell, so render it (`force_fetcher='stealthy'`); tiny body + large page total means dhole's reader missed this markup, so do NOT spend 3-5s on a browser that will hand back the same few characters — take `extraction_type='html'` (or `'text'`) instead. A genuine link index is `ok` even when it is thin, because there the links ARE the content. `content_ok=true` beside a small `total_extracted_chars` still means "answered with very little", which is a different fact from "answered with nothing". Login-walled sites (out of scope) and DataDome / Akamai / interactive Turnstile cannot be beaten — say so honestly.

**Trimming and pagination**: `focus` returns only relevant blocks (header notes "showing N of M blocks"; `focus:''` gets the full page). A **block** is not one paragraph: blank lines, ATX headings, tables, code fences, horizontal rules and the start of a list run are all boundaries, and anything past 2,400 characters is broken at the nearest sentence end — so a page whose paragraphs are glued by single newlines (a flattened docs page, the shape that used to arrive as one indivisible block) still comes back as rankable pieces. Fences and tables are never broken: two lost sentences of prose still read, three lost rows of a table are fake data. The two counts are on the envelope as `focus_blocks_total` / `focus_blocks_kept` too, because that header line is body text and a continuation page no longer carries it. The same header **names any table or code block the filter deleted** — "dropped the page's only table (280 chars) - it shares no token with your query" — because losing two sentences of prose and losing the answer are two different events and a block count cannot tell them apart. A block is only protected when it shares at least one word with your query, so a table whose cells are numbers and English labels vanishes to a Chinese query. When nothing was cut at all (`focus` given, page is one block), that is said in `summary` as `focus was NOT applied: …`. After truncation, continue with `offset=next_offset`, re-passing the same focus — but if `next_action` says focus "is already on this call and it dropped …", re-narrowing with that same query deletes it again; `focus=''` gives the page back. `max_content_chars` spans 500–200000. **A cap you named can still be passed** — if what remains of the page after your window is shorter than the 500-character minimum window that would be worth a second call, the tail merges into THIS window and `summary` says so in one sentence: `max_content_chars=1200 was passed by 246 chars: what remained of the page is shorter than the 500-character window that would be worth a second call, so it came along with this one - nothing was dropped, there is no next offset`. Read it as a budget fact, not a truncation: `is_truncated` stays false and `next_offset` stays 0 because there genuinely is no next page, and no character was cut. A page that fits under your cap never mentions the parameter, and neither does a read that ran on the default budget — with no cap named there is no instruction to report on. On a continuation slice the sentence counts THAT slice (`delivered - cap`). The 50MB body cap gates BEFORE download — oversized bodies fail immediately and raising `timeout` won't help. Default block picking is BM25 keyword overlap; `focus_engine="neural"` scores blocks **semantically** instead (model missing = an explicit error, never a silent download; `focus_mode="best"` returns the single top block plus its heading — the "which paragraph answers this" mode; best mode reports the same dropped-table note, and it drops more than filter does).

**`cache_ttl` — what `0` does and what it never did** (web_read / web_crawl / web_search). `0` is a **read-side** instruction: this call consults no cached body (and, for `web_search`, re-asks the engines). What it fetches **is** stored, under the tool's normal TTL, so the next default-TTL call continues from the freshest copy instead of replaying an older one — an earlier build dropped the fresh body on the floor, which made "force a fresh look, then carry on with a normal read" return the OLD page (the read after a 4.4-second refresh was staler than the refresh). Two kinds of call still store nothing, and they say so by name rather than by borrowing `cache_ttl`: **an action chain's page** (`web_act` — that body only exists after the actions, so replaying it answers a question the chain never asked) and **a write's answer** (`web_request` with a non-GET method — a POST receipt is not shared content). A **negative** value is not a duration — it is clamped to `0` and the summary says so (`cache_ttl=-1 is not a duration; using 0 - this call reads no cache, and the copy it fetches is stored like any other read`); it is never silently rewritten. Cache hits are keyed by URL plus the request fingerprint (cookies / auth / session / pinned tier), never by who was logged in — see the credential recipe in `recipes.md`.

**An out-of-range number is either clamped-and-named, or refused — never silently rewritten.** Which one depends on whether the value you sent has one sensible reading. A **resource cap** you exceeded (`max_content_chars`, `max_links`, `max_pages`, `max_depth`, `concurrency`, `max_total_chars`, `max_results`, a floor like `min_relevance`, an action's `wait`) is clamped to the documented bound and `summary` names it (`max_content_chars clamped 1->500 (supported range 500-200000)`; `max_results=100 is outside the supported 1-50 range; returning at most 50`) — so a short answer is never mistaken for "there were only that many". A value whose nearest legal reading would **change what you meant** is refused instead, naming the argument and its range: `offset=-5` (`offset must be between 0 and 2147483648, got -5.`) rather than being read as `0`, and `page=99` (`Invalid page: 99 (0-10)`) rather than `10`. Every clamp is announced in the same field on all three tools (`summary`); nothing is adjusted quietly.

**`focus_engine` picks the scorer per call** (`"bm25"` | `"neural"`). There is no machine-wide license anymore — omitted or `"bm25"` always runs the cheap keyword focus, `"neural"` runs the local cross-encoder for this call only (~12.5s of CPU per page plus a ~280MB model, which is exactly why it is never the default). `"neural"` with the model unusable is **refused** (`neural_focus_model_missing`, no request sent, no silent download), and the refusal says WHICH thing is wrong: the files are not on disk yet - a plain `web_search` fetches them on its first run under its default `mode` (resumable; it has no `focus_engine`); or the files ARE on disk and the reranker would not load - the reply carries what this process recorded (a missing runtime, a failed load), and there is nothing to download. It applies to `web_crawl` too, where the per-page cost multiplies by `max_pages`.

**PDF**: `pages=` only trims **extraction** — the file still downloads whole, and a download is **one HTTP attempt of at most 30s**, so raising `timeout=` past 30s buys the call room to *parse and OCR* what arrived, not a longer download (`timeout_applied` names the figure when the ceiling bit). `pages=` and `password=` are **PDF-only**: when the answer that came back is not a PDF (an HTML page, JSON, a login redirect served at a `.pdf` URL), neither one was consulted and `summary` says so by name — nothing was trimmed, nothing was unlocked, and the body is what a call without those arguments gets; the value you passed to `password=` is never echoed back. Responses carry `table_of_contents` (titles + page ranges) — pick pages from it. A title the page box wrapped onto several lines is **one** entry, not one per printed line: the fold is decided from geometry (same dominant size, same weight, next line within one line gap, no table in between), so a two-line cover title and a narrow-column heading each come back as a single section — which matters because `pages=` is chosen from this list. Scanned or CID-broken PDFs auto-OCR. A table with merged cells comes back as **one labelled line per row, not a markdown grid**, preceded by `[merged-cell table: N merged cell(s) …]`: markdown cannot carry a cell that spans columns, so a grid would present the second header row as data and the covered positions as blanks ("Fourth quarter" landing in a data row is that error, not a coincidence). The span is stated on the cell that owns it (`[spans 2 columns]`), and a value carried down from an earlier row is written `(as row 1, column 1)` rather than repeated or left empty. Rectangular tables are unaffected — they still render as a grid. `summary` says `table(s) with merged cells rendered as text rows` whenever a page had one, so the shape change is visible without reading the body. Pages that **draw** rather than write — charts, diagrams, embedded pictures — are accounted in `metadata.figures` (`page` + `raster`/`largest_px` for pictures, `vector_objects` for drawings) and named in `summary` (`1 of 4 page(s) carries non-text content this extraction does not render`). What counts as a drawing is extent, not ink: table borders, dividers and `<hr>`-style rules are excluded (a page of prose with three rules is not a figure page), while a chart drawn with 1-2pt strokes still counts, because its marks enclose an area. Nothing is inserted into `content` for a figure, because a placeholder string is characters the extraction did not actually recover. So a page that comes back with only its caption is not an empty page: read that page with a vision tool or a `web_act` screenshot.

**`css_selector` applies to HTML only**: on XML/JSON/plain text it matches nothing — the whole document comes back and `summary` states the selector was not applied. Don't mistake the full payload for your slice.

## Page interaction (actions, via the stealthy browser)

The chain is **`web_act`'s** alone: `web_read(url=, actions=)` is refused and the refusal names the door (`web_read` never touches what it fetches, and a chain does). Actions run in order; each leaves a receipt in `metadata.actions`.
- `{scroll:n}` or `{scroll:{steps,selector,ms_per_step}}`: scrolls to the bottom, then polls the DOM until the page **stops growing** (chases the new bottom, two quiet rounds ends it), capped at a 20s budget — and it dispatches a real `scroll` event, because when the viewport is tall and content short, `scrollTo` fires nothing and event-only lazy-loaders never wake
- Sites gating lazy-load on `event.isTrusted` ignore synthetic scrolls — use `{click:'<css of the load-more button>'}`; forms take `{fill:{selector,text}}` + `{press:'Enter'}`; `{wait:ms}` / `{wait_selector:'css'}` (or `{selector,count,state,timeout_ms}`) hold for elements
- **Hover reveals, drag moves**: `{hover:'css'}` (or the `{selector|index, expect?}` dict) hovers to expand menus and tooltips — hover menus render synchronously, so the settle only waits for the DOM to go quiet (2s budget), no navigation wait. `{drag:{selector|index, to}}` drags one element onto another — BOTH ends take the same target shapes (`{drag:{index:3, expect:'滑块', to:{index:7}}}` is legal); a drag without a `to` is refused at validation, not silently a no-op. Sortable lists and slider handles are the real use
- **No selector? snapshot first**: `{"snapshot": true}` returns a numbered list of interactive elements (index/tag/role/name, capped at 80 with `elements_truncated` + `elements_total` when cut). Then address by index: `{click:{index:12, expect:'登录'}}`, `{fill:{index:3, text:'...'}}`, `{press:{index:7, key:'Enter'}}`. **A bare row number is the same address** — `{click:12}`, `{hover:3}`, `{read:5}`, `{submit:4}`, `{screenshot:2}`, and a drag's `to:7` all normalize to `{"index": N}` byte-for-byte, because the number that list shows is the number you send: an agent that reads that list writes the number back bare — the dict wrapper was never meaning, it was typography. The dict is still needed when something rides BESIDE the index (`expect`, `text`, `key`, `confirm`, `as`, the screenshot knobs), and three doors deliberately stay closed: `fill` without `text` is not a fill, `press`'s bare value is the KEY name (`{press:5}` would read as "press the key named 5"), and `drag` needs both endpoints so a single number says nothing. Snapshot and actions share ONE interactive-element selector in document order, so indices reproduce across page loads; `expect` verifies the element's visible name before acting — a stale index fails loudly naming what sits there now, instead of clicking the wrong thing. **That name is the element's stable identity** (aria-label / its own visible text / associated `<label>` / placeholder / `name` / `id`) and never what a form field currently holds: the snapshot's name column and `expect` read one and the same ladder, so `{"fill": {"index": 3, "expect": "手机号"}}` still matches a field that already holds a phone number, while an `expect` of the typed value never matches. Verifying "the text I typed is on the page now" is `{"read": {"property": "value"}}`'s job (see the `attribute_says` pair), not `expect`'s
- **Submit is gated**: `{"submit": {selector|index}}` is the explicit irreversible step — and so is a `{"click": ...}` whose target IS one (`input[type=submit]`, an `input[type=image]`, or a form's default button): the gate reads what the action DOES, not the action's name, so such a click pauses exactly like a submit. Without `"confirm": true` it PAUSES: a `pending_approval` receipt, nothing submitted, the response's summary/next_action tell you to describe the submission to the user and re-run the same actions chain with `{"confirm": true}` on that submit (on a gated click the confirm rides the click: `{"click": {"index": N, "confirm": true}}`; a string-selector click has to be re-addressed in the dict form to carry it) after a yes. Paused and confirmed runs both land in the write audit. Never set `confirm: true` yourself without the user's explicit yes. When your client supports elicitation, dhole asks the user directly (a popup; the submission never runs without their accept) — your `confirm: true` does not replace that ask, and a decline or an ask that cannot reach a human is final: re-running asks again, no parameter skips it. The receipt's `submitted` is earned by a request actually leaving that page (`submission` names its method); a target no click submits (a `<form>` itself) answers `not_submitted: true`, and the write audit does not see that row
- **Screenshots** are always available, in two targets: `{"screenshot": {selector|index}}` (or the bare row number `{"screenshot": 2}`) crops ONE element, `{"screenshot": {"full_page": true}}` captures the whole scrollable page (mutually exclusive — an element crop is already bounded by the element's own box). A capture always has to name something to look at: `snapshot` is the only action in this family that takes a bare boolean (`{"screenshot": true}` is refused, and the refusal names both doors). Knobs on either: `image_type` (`png`|`jpeg`, default png), `quality` (0-100, jpeg only), `decode_qr` (local QR decode — deterministic OpenCV work, the texts land in the receipt) and `save_to`, which writes the file and reports its absolute path + byte size instead of putting bytes on the transcript (inline captures cap at 2MB; `save_to` is the route around that cap). Captures ride the response as image blocks, not base64 in JSON. Captcha discipline is part of the tool description: ≤3 attempts on image captchas then hand off to the user; DataDome / Akamai / interactive Turnstile / 2FA / sliders are always hand-offs — dhole is a tool layer, cracking is not its business, and **dhole ships no vision model**: the reading happens in you, so an element capture is for the image you can read yourself.
- **`read` takes THIS page instance's text back into the chain**: `{"read": "css"}` crops nothing and captures nothing — it reads the element's rendered text into the receipt (`read: "K7Q2Z"`), and `{"read": {"selector": "css", "as": "code"}}` also stores it under a name so a later step in the SAME chain can answer it: `{"fill": {"selector": "#answer", "text": "{=code}"}}`. Knobs: `attribute` (read the markup's own `href` / `src` / `data-*`), `property` (read what the page holds NOW — one of `value` / `checked` / `selected`, the three a `fill` actually changes), `expect`, and index addressing (`{"read": {"index": 7}}` from a snapshot row). **The two layers are not the same number on a form field**: markup ships `<input value="1">`, a `fill` of "3" moves the DOM property and never rewrites that attribute, so `attribute:"value"` on a box would hand back "1" while the page holds 3 and a later POST carries 3. Because that reading is exactly the check people run before an irreversible submit, `attribute:"value"` on an `input`/`textarea`/`select` is answered from the live layer and the receipt says so (`read_via: "property:value (asked as attribute)"`); when the two layers disagree, the markup's own number rides along as `attribute_says` — **the pair being unequal IS the proof the fill landed**, in one call. Non-form elements are never switched layers (`get_attribute` as asked). A read that finds no text FAILS that step and names the two other doors in its receipt error: `{"property": "value"}` for a field's live value, a `screenshot` action for a challenge drawn as an image — an empty `read` is never reported as a success, and a property the element does not have fails by naming its tag rather than returning `""` (an empty box and a `<div>` that has no value at all must not look alike). `{=name}` reaches **backwards only**: a reference to a read that has not run yet is refused by name, and a reference whose read ran and failed refuses the fill too (nothing goes in, and that row says to look at the read's row). A literal `{code}` in text is just text — a reference always carries the `=` (`{=code}`). `read` caps at 2,000 chars **in the receipt** and says so (`read_truncated` + `read_chars_total`); the value handed to a later `fill` is the whole text, because a half-truncated answer is worse than a long one (a substitution that would overrun `fill.text`'s 5,000 is refused, not cut)
- **Why the in-chain read exists at all**: by default every `web_act` call navigates, so a challenge read on one call belongs to a page instance that is already gone on the next — retrying across calls answers the *previous* challenge (measured on the local target: it issues a new token per `GET`, and the answer typed on round 2 was round 1's). Rounds therefore only help when the site binds the challenge to the session. `pin=true` is the door that removes the structural part of that failure: it keeps THIS page on that session, and the next call that also passes `pin=true` on the same site acts on it **without navigating** — so the token, the image and the half-filled form are the ones you already looked at. What it takes to hold: `session_id=` (an anonymous auto session is shared and recycled, so there is no page of yours to keep — `pin` is refused with that reason in the `summary`, never silently), one URL per call (a batch fetches in parallel; one page cannot be pinned by two of them), and not a CDP attach (those are the user's own tabs). It is released after 300s, when the host changes, when the page is closed, or when the session closes — and each of those drops says so in the `summary`, because the one thing you must not do with a stale pin is answer last call's challenge. `submit` on a pinned page pauses with a longer sentence: "re-run the same chain" is only half true there, since the earlier fills already ran. When the challenge is **text in the DOM** and you are inside one call, one chain still reads it, answers it and submits it against the instance still alive: `read → fill → submit`. When the challenge is an **image**, no in-chain read can help — a `screenshot` capture reaches you only after the chain has run, so you cannot type what you cannot yet see; that is exactly the case two pinned calls solve (read/capture on call 1, fill/submit on call 2), and `{"screenshot": {"selector": ..., "decode_qr": true}}` is for the QR-shaped ones and for showing a human what to type
- On a JS-shell page (SPA) the post-action readback is still the shell's "enable JavaScript" text — that is what the DOM holds. What happened is in `metadata.actions` (one receipt per action); to SEE the rendered state, add a `screenshot` action to the chain

## Structured extraction (schema)

Repeated records REQUIRE a "container selector + sub-schema" — sub-selectors evaluate **inside** each container, one record per container. A bare top-level selector returns the page-wide union; "which tag belongs to which quote" simply doesn't exist in that output. A property without `"type"` returns the FIRST match; `"type": "array"` returns all of them. Max 200 records per field, 8 nesting levels; only `selector` / `attribute` / `type` / `properties` / `items` are read — any other JSON-Schema keyword is ignored; sub-selectors pass the same injection validation. Example:

```json
{"properties": {"quotes": {"type": "array", "selector": ".quote",
  "properties": {"text": {"selector": ".text"}, "tags": {"type": "array", "selector": ".tag"}}}}}
```

The top level of a schema is for page-wide scalar fields (and `"type": "auto"`) only — a `selector` or `type: "array"` there is refused before any request, with the container shape spelled out. And when a well-formed schema returns far fewer records than the page visibly holds, suspect the container selector first: one that matches a single wrapper (or a wrapper the page has only one of) yields exactly one record.

### `schema="auto"`: no selectors, and a schema you can reuse

`schema="auto"` (the bare string; `{"type": "auto"}` and `{"mode": "auto"}` are the same thing) asks dhole to work out the page's structure itself. It needs no selectors and detects, in order, JSON-LD → tables → lists → OpenGraph, falling back to a visible-text summary. On top of that it **proposes a schema**: when the page has a repeated structure — a `tag.class` group that occurs 3+ times with text inside — the reply carries a `_schema` you can paste straight back into `schema=` for the sibling pages of the same site, instead of guessing the selectors again:

```json
{"_mode": "auto", "lists": [...],
 "_schema": {"type": "object", "properties": {"book": {"type": "array", "selector": "li.book",
   "properties": {"title": {"selector": "h3.title"}, "price": {"selector": "span.price"}}}}}}
```

Feed `_schema` back in and you get the grouped records (`{"book": [{"title": "Alpha", "price": "$10"}, ...]}`) — the same container/sub-schema shape the section above requires, derived from the page rather than hand-written. Two things to read it for:

- **It is a heuristic, not a guess at meaning.** The container is the most-repeated `tag.class` group; each field's name is the last token of its class (or the tag name when there is no class), and classless generic tags (`div`, `span`, `p`) are not proposed as fields. Treat `_schema` as a starting point to copy and rename, not a verdict — a field called `link` is a `<a class="link">`, not an assertion that it is the one you want.
- **No `_schema` key is an honest "no structure here", not a failure.** A page with no repeated container (an article, a single record) proposes nothing; the auto extraction's JSON-LD / tables / lists are still returned. And a field count is capped (8), so a wide row proposes its first eight named descendants — the cap is a prompt to narrow the schema, not a truncation to miss.

## Two layers in one call (`nested_*`)

`schema` nesting scopes selectors **inside one document**; it cannot reach a second page. When the items you want each live on their own page — 8 featured collections and the works inside each, a result list and its detail pages — that is a fan-out over URLs, and `nested_selector` + `nested_fields` do it in one call instead of nine:

```json
{"url": "https://quotes.toscrape.com/", "nested_selector": "div.quote",
 "nested_fields": [{"name": "author", "selector": "h3"},
                   {"name": "born", "selector": "span.author-born-date"},
                   {"name": "description", "selector": "div.author-description"}]}
```

Measured on that call: 8 records (10 containers, 8 unique authors), 8.2s, `summary` ending `nested: 8 links expanded, rungs=2, ok 8 / empty 0 / failed 0`. Read the four things the fan-out owes you:

- **The href is taken from the matched element, its first descendant `<a>`, or its nearest ancestor `<a>`** — in that order. So `.topic-card` works even when the card is a `<div>` holding the link, which is the common shape.
- **`nested_fields` runs on the second-layer page only.** Nothing from the list row rides along — if you need the card's own text next to its detail page's fields, extract it on the first page with `schema=` in the same call (the two results sit side by side in one JSON object). A field whose selector misses is **not** guaranteed to come back `""`: three name-based backfills still run on that page — the page's own metadata (OG / JSON-LD) when the **field name** matches a metadata key, then JSON-LD by field name, then a pattern search over the visible text. So a field called `title` / `author` / `date` can arrive filled from the page's shell even though its selector hit nothing, and `""` (or `[]` for `type: "array"`) is what you get only after all four miss. A record where *every* field missed is `fields_no_match`, and a run where every page missed is `nested_empty` — both failures, not answers. A record that failed carries its own `diagnosis` twin (`{code, retryable, recover_with}`, same reader as every other receipt: that 404 row says `http_error_404`, that missed-everything row says `fields_no_match`), and a record that came back clean carries neither key. Name the element that holds the value (`div.author-description` for the bio above), not the bare tag: on that author page `{"selector": "p", "type": "array"}` returns Login / copyright / credit paragraphs — a hit that is not the answer.
- **`truncation=nested_budget` means "there were more, and raising the cap gets them"** — the default expands 8 links and the ceiling is 30. Duplicates and href-less matches are counted in a separate note (`links: 5 elements matched → 2 unique, 2 without a usable href`), because re-raising `nested_max` recovers neither. A list page with 12 sections answered by 8 records is only correct if you raised the cap or said so out loud.
- **Each second-layer link passes its own robots.txt check before any request** — the fan-out took that job off your hands, so a disallowed item comes back as `{"error": "robots_disallowed"}` with `robots_skipped` counted in `summary`, and nothing was sent for it. If you would have checked per URL by hand, the tool now does it as part of the call.
- **A column that comes back the same everywhere is named in `summary`** (`nested fields: 介绍 came back identical on all 4 second-layer pages - either those pages really share that value or the selector is grabbing page chrome`). `ok N / empty 0` counts whole pages, so a run where every page yielded *something* — but the wrong something — used to read as a complete success; the bio-selector mistake in the bullet above is exactly that shape, and it is now reported rather than left for you to notice. Same for a column that is empty on every page while the others fill. Both are `ok` deliveries with a warning, not errors: the values you got are still the values, and re-deriving one selector is one call, not a rerun.
  - **What this warning cannot see: a selector that is wrong in a different way on every page.** It compares values across records, so it sounds only on an *identical* column (or an empty one). A selector that lands on each page's own chrome — the measured `books.toscrape.com` shape, where every author page has its *different* sidebar/footer text — produces N distinct wrong values and passes silently, and the name-based backfills above can make it look like a real answer. Nothing in the response marks it. The check is yours, and it is one call: read **one** second-layer page without `nested_*` (or with `css_selector` on the container) and compare it with what that field returned, before trusting a fan-out of eight.

**More than 30 second-layer pages** is no longer one read: take the link list with `schema={"properties":{"href":{"type":"array","selector":"a.card","attribute":"href"}}}` on the first page, then `web_read(urls=[...])` in batches — `schema=` combines with `urls=` (one schema applied to each URL, so a batch of detail pages comes back as grouped records), and 30+ URLs is where `web_crawl` / `web_discover` become the cheaper map.

Second-layer pages are read as whole documents (like `schema=`), so a field's `type: "array"` is what separates "the one title on that page" from "the 20 works listed there". Concurrency is 6 lanes. Not combinable with `urls=`, `cdp_url=` or `actions=` — each of those would silently drop one side, so the call is refused before any request goes out. A call is cache-addressable like any other, **including its fetcher tier**: pinning `force_fetcher='stealthy'` within the TTL can be answered by the copy that tier already produced, so add `cache_ttl=0` when you need that tier to re-visit the site (after a login, or after the first read looked like a shell).

## web_request: one write, sent once

A non-GET is its own tool: `web_request(url=, method=, body=, content_type=)`. `web_read` refuses `method=` — reading and writing are different jobs, and the write's rules used to live in a branch of the read.

- **Never retried**, for every verb that changes state: POST, PUT, PATCH and DELETE all go out exactly once, because the previous attempt may already have committed and re-sending writes twice. That is a rule dhole sets for itself, not a reading of the spec — RFC calls PUT and DELETE idempotent, which is a claim about the endpoint, and a client cannot check it. (GET and HEAD remain retryable: asking twice changes nothing.) A timeout therefore means "unknown", not "failed" — check with a read before you send again.
- **Never cached, never escalated, never answered from a snapshot**: the answer comes from the server's reply to this request. A browser replay would answer about a GET to that URL, and an archive snapshot is one GET from some past day — neither has seen your write.
- **`HEAD`** is here rather than in web_read because it is a request shape, not a content read: status + declared length + type, no body.
- **Bodies cap at 256KB**: this retrieves, it does not upload. A dict becomes a form (urlencoded, or JSON when `content_type` says json); a string goes out as-is. A `content_type` that dhole cannot encode the body *into* is refused rather than sent as a lie: `content_type="text/plain"` + a dict used to go out with a `text/plain` header over `a=1&b=2` bytes, and the receiving server believes the header. Either send `body=` as a string (goes out byte-for-byte, your header is then true) or `application/x-www-form-urlencoded` / `application/json`, which is what a dict really is.
- **Credentials are not a parameter** — `cred_defaults` stores them per host and the request carries them; `identity_applied` names what ran. That is the rule on the three doors that fetch pages (`web_read` including its `urls=[...]` batch, `web_request`, `web_crawl` whose every page carries the stored credential of its host). **`feed_read` is the exception and it says so on the row**: a feed fetch goes out with no credential at all, so when you have a token stored for that host the items you get back are the public view — the row's `note` names what is held and that it was not sent. The match is host-scoped on every door: nothing stored for `api.example.com` ever rides to another host.
- **`headers=` is the non-credential half of that sentence**: name the keys the endpoint's own documentation asks for (`X-Request-Id`, a `Content-Language`, an API version header) and they go out as written, winning key by key over what dhole synthesizes. The three families that belong to another door — `cookie` / `authorization` / `proxy-authorization`, `user-agent`, `if-*` validators — are refused by name here exactly as they are on web_read, with that door in the sentence. Full shape and caps: the `headers=` section below.
- **No `anti_detect` here**, deliberately (the reading tool lists 7 names for this tool; the 7th does nothing): a write never renders, so there is no ladder to choose — the HTTP tier is the whole request.

Unknown verbs are refused with the list of the five, before anything is sent; `method=GET` is refused with a pointer to web_read — GET stays out because **web_read owns** the cache, the escalation ladder and the archive fallback, and a write must not be read through those. Sending a write is the one call worth checking first: `web_read` follows redirects and reports where a URL actually lands.

One more gate shape, decided per connection: on a client that supports elicitation, dhole asks the HUMAN at the gate (a popup naming the method, URL, body shape and the credentials that ride along) instead of waiting for a model-signed `confirm=true` — accept sends the write, decline or an ask that cannot reach a human refuses it, and no parameter replaces that ask. Clients without elicitation keep the `confirm=true` path above, unchanged.

## What `readOnlyHint` promises (and what it leaves to you)

Four tools carry `readOnlyHint: true` on the wire: web_read, web_crawl, web_discover, feed_read. The promise is exact and code-backed: they send GET requests only (anything else is web_request's gate above), and their local writes are process bookkeeping — the body cache, the cookie jar a site's session left, engine cooldowns. Identity is the one border: a `cdp_url` attach rides your logged-in Chrome, which is why an attach to a host stops at `cdp_authorization_required` until you approve it — per host, and that approval is re-asked after 30 days rather than trusted forever. On an elicitation-capable client that approval is a popup to the human (accept authorizes the host, decline or an unreachable ask executes nothing, and re-calling asks again); on other clients `confirm=true` re-call remains the door.

A host that auto-approves readOnly tools on this hint should know what that includes: `ignore_robots=true` is a compliance call the agent makes itself — no human gate sits behind it. The hint is true; it is not supervision.

## Credentials, cookies and sessions
- **`auth` and `cookies` are stored, not passed** `cred_defaults` `set={auth: ..., host: "api.example.com"}`. `auth` shapes are `{type:'basic',username,password}` / `{type:'bearer',token}` / `{type:'header',name,value}` (for `X-API-Key`-style headers — a one-off custom header is not a thing any more; the stored `auth` of type `header` is how such a site is reached). It only places the header — **no OAuth flows, no token refresh**; when a token expires, store a fresh one. Credential **values** are never echoed anywhere; bodies fetched with credentials are cached per-credential (an admin view is never replayed to anonymous requests). `headers=` does not reopen this: it refuses `cookie` / `authorization` / `proxy-authorization` back by name, because a credential typed into a call is a credential that forgot which host it was written for
- **Credentials do not survive cross-origin redirects**: cookies and `Authorization` go only to the origin you named; a hop to another domain strips them (same-host hops and hosts already holding that cookie in the jar keep them)
- The `session_id` cookie jar is kept per host (24h expiry; responses report cookie names, never values) **in memory** — `DHOLE_PERSIST_CREDENTIALS=1` moves it to disk encrypted. It **spans both tiers**: a NAMED session's dedicated stealthy browser is seeded from the jar before navigation and harvests new cookies back after — HTTP-tier login state rides browser calls too. Boundaries: the shared auto session is never seeded (that would pour session A's login into session B); CDP attach never bridges (it runs your real Chrome profile, read-only). Roster and cleanup: `sys_state` (no args = the roster, `clear=["<session id>"]` forgets one, `clear=["sessions"]` with `confirm=true` forgets all)
- **`check_login=true` is answered by the browser tier only**: an HTTP-tier result or a cache hit returns an explicit `{logged_in: null, method: "unavailable: …"}` in `login_check` with the reason — a MISSING `login_check` field means "not requested", never "checked and nothing there". To actually probe: re-call with `force_fetcher='stealthy'` (add `cache_ttl=0` for a cache hit) or `cdp_url=`. `logged_in: false` = session expired → hand back to the user to re-login; `null` = page shape undecidable → say so, don't treat it as success
- `<meta http-equiv=refresh>` is followed on both tiers (the HTTP tier may not follow delayed refreshes; `metadata.meta_refresh` records the hop origin)

## Conditional requests (304 is a success)

**Conditional requests are dhole's own business**: no parameter puts conditional headers in your hands — the one public trigger is `extraction_type='check'` (below), which asks the origin "did it change" with them — and an ordinary call never sends a conditional header and simply gets the body. `headers=` refuses `If-Match` / `If-None-Match` / `If-Modified-Since` / `If-Unmodified-Since` / `If-Range` back by name, with that door in the sentence: the browser tier cannot carry a validator (it renders an empty view and reports status 0), so a call that could escalate would answer a different question than the one you asked. Reading rule that survives: `status=304` with `content=[]` is **success**, never a failed fetch, and must not escalate to the browser (there is no body to render by definition).

## Headers you name (`headers=`)

**Your keys win, key by key** — on both tiers, over what dhole puts on the wire. Measured against a local echo site (the request that arrives is printed back): naming `accept-language` replaces the generated one, naming `sec-fetch-site` replaces dhole's value, an `X-…` name you invent arrives exactly as you wrote it. Caps: 50 names, 8KB per value; values are strings (`null` sends the empty value), a name with a line break in it is refused as header injection, and `Host` / `Content-Length` / `Transfer-Encoding` / `Connection` belong to the HTTP stack itself. One rejected name stops the call — half a header set is a request nobody asked for.

**Adding is not replacing.** An ordinary `web_read` sends about fifteen headers that nobody named: a generated `User-Agent` with its `sec-ch-ua` family, `accept`, `accept-encoding`, `priority`, and a `referer: https://www.google.com/` that dhole invents because walls score a navigation with no referrer. `headers=` rides on top of that template and says so in `summary` — it is not a way to send *only* your request shape. The dial that does that is **`anti_detect='off'`** (see the rung section), and it names itself in the same field when it bites.

**Three families are refused by name, each with its own door** — the refusals are the boundary, not a gap in the parameter:

- `cookie`, `authorization`, `proxy-authorization` → **`cred_defaults`**, which stores them *for one host*. That scoping is the whole reason they are not arguments: a credential you type per call rides to every redirect hop you never named, and it lands in the transcript with the call
- `user-agent` → the TLS profile it is paired with: the HTTP tier picks its impersonation OS from dhole's own generated UA *before* your dict is merged, so a UA you name would go out with another browser's handshake under it. `anti_detect='off'` sends the client's own matched pair; `cdp_url=` runs the user's real Chrome
- `if-*` validators → `extraction_type='check'`, the one door above

**On `web_request` the two doors above are not parameters.** A write never renders, so that tool takes no `anti_detect=` and no `cdp_url=`, and its `extraction_type` has no `check` value (the changed-since-last receipt is `web_read`'s). What a write CAN do: drop the refused name and send the rest — the request goes out on dhole's matched UA + TLS pair — or put the rung on the store every call reads, `cred_defaults set={"anti_detect": "off"}`. Advice generated for a write says exactly this; a refusal that told you to pass `anti_detect='off'` to `web_request` would only earn you a second call that dies on `Unsupported argument(s)`.

**Anything else you invent is not a principal to dhole**: it travels the redirect chain, including a hop to another origin (only those three names are stripped off-origin, because only they name who you are). So a header that authenticates you — an `X-API-Key`-style one — belongs in `cred_defaults` as `auth` of type `header`: that path knows its host, strips it off-origin, never echoes its value, and names itself in `identity_applied`.

**Headers change the answer, so they change the cache key**: two calls to one URL that differ only in `headers=` never replay each other (`accept: application/json` and `accept: text/html` are not the same document). `urls=[...]` carries the same dict to every row, and a write through `web_request` takes the same parameter with the same refusals.


## web_read: batches, links and the local waiver

`urls=[...]` batches in parallel; `include_links` caps each link class at 30/20/20 (`max_links` up to 100) with `total_found` reporting the pre-truncation count; `include_media` adds up to 20 image URLs to `links` (each candidate is unescaped and validated first — a `lazy-src` holding two concatenated URLs, an `&amp;`-mangled query, or an address with whitespace in it is dropped rather than shipped as one unusable string). A proxy from `cred_defaults` is credited as an explicit proxy, so it gets a 5s TCP precheck — an unreachable one returns `proxy_unreachable` with no request sent. Local dev services need `cred_defaults` `allow_private` (true = loopback, or an explicit host list); nothing private is fetched before that waiver exists. Once it does: a **forced browser read** of a private target dials that target **twice** — first a liveness probe (direct, 3s, no retries, no synthetic headers, no redirect hop, because a browser cannot reach a dead backend either), then the browser navigation. `summary` names the probe on that call (`this call makes 1 extra direct request to the target before the browser runs`), so two lines in your own service log are accounted for rather than looking like a retry.
**The auto path probes before the tier it picks has run, and no field says so.** With no proxy in
play, the probe buys a verdict, not an answer, and it only ever gets to decide on a private target —
so that is the only target it dials. Loopback and private ranges have no legitimate service that
answers after two seconds, and a browser forced onto the same dead port would wait out the same
silence; a dead local port settled in 2,812ms as `error=network_error: timeout (TCP preflight)` with
`escalation_path=preflight:timeout(skipped_http+stealthy)`, which is precisely the 30s silence
this exists to remove. On that leg one write is **two TCP connections, one of them carrying zero
bytes** — **one probe per URL** — and the request itself went exactly once, so neither connection
is a retry (measured against a local counter: a batch of 8 local URLs is 16 connections, 8
requests + 8 connections carrying zero bytes, the ratio holding at 2.0 across four shapes).
That cost belongs to the auto ladder, not to the tier: a forced `http` read pays no probe at all —
same counter, same target, **one connection, none of them carrying zero bytes** (the auto leg on
that very target was two). The forced browser leg does pay one, and names it in `summary`.
A cache hit pays nothing: the answer comes from the jar before any dial (measured: 0 connections).
With an explicit proxy the probe lands on the proxy endpoint instead (measured). **A public
target is not dialed at all**: out there a TCP refused can come from a middlebox that answers and
then fails, so no decision could rest on it, while the dial itself costs the handshake plus up to
2s (measured on three live hosts: 383 / 50 / 44 ms) and leaves nothing in the receipt to ask about
(`escalation_path="direct:http"`, `preflight` appearing 0 times). If your own log shows a
connection that carried no request to a local service, that is this probe: it is not a retry, and
it is not a second attempt at your write.

**`url=` and `urls=` are one or the other.** Passing both is refused before any request goes out — the reply is one `invalid_request` row per URL you wrote, `successful=0`, nothing fetched — because the only ways to resolve it pick one side and silently lose the other: a batch that drops the URL you named first reads, from the caller's seat, exactly like a batch that read it. Put the single page in `url=`, or put every page (that one included) in `urls=`.

## anti_detect: one dial, four rungs

**One dial, four rungs ** — `off` (no hardening, and since the headers work no synthesized request headers either: use it when the camouflage itself is what a site trips on, or when you want to be the one who said what went out), `basic` (canvas noise + WebRTC block), `auto` (the default, and the tested-against-real-walls configuration; also runs the Cloudflare challenge path), `aggressive` (auto + loads every resource the page requests, which is what a real browser does — slower, and the rung to try when a site scores the missing subresources). No fifth rung and no per-knob override, deliberately: those settings only work as a set, so the six arguments that used to expose them (`headless`, `real_chrome`, `hide_canvas`, `block_webrtc`, `solve_cloudflare`, `useragent`) are gone as parameters. Two of them were capabilities you may expect back: a hand-set User-Agent is a **stronger** tell than none (the UA has to match the TLS fingerprint the HTTP tier impersonates and the browser tier's fingerprint profile — mismatching pairs are exactly what scanners look for; `headers=` refuses `user-agent` for that reason, and the two doors that stay self-consistent are `off` and `cdp_url=`), and forcing the installed-Chrome channel turns "Chrome is not installed" from a fallback into a hard failure — dhole already uses the installed system browser where it exists (Chrome first, then Edge), so that rung needs no argument.

**What `off` changes on the fast tier is measured, not asserted**: a call that names nothing puts 15 headers on the wire at `auto` (a generated UA and its `sec-ch-ua` family, `accept`, `accept-encoding`, `priority`, and a `referer: https://www.google.com/` that dhole invents) and 14 at `off` — every one of them the client library's own, with no referrer. `auto`'s 15 are now **one face held for the whole process** — one roll per browser family per process (`one face per process`), so the retries of one call, every URL in a `urls=[...]` batch, and every escalation inside the same dhole process all present the same browser. It is asked for the family the handshake impersonates and for a desktop shape, which is what makes those 15 one browser's: before that was measured, 8 sessions in one process presented 7 different faces and 3 of 16 requests carried a phone UA next to a desktop `sec-ch-ua-platform`. Restarting the process re-rolls; no parameter picks the face. What survives the roll is the invented referrer — and `sec-fetch-site` is no longer one of the things that survives it: the header generator writes `"?1"` there (a value real Chrome puts in `Sec-Fetch-User`, not here), and dhole now **drops** any fetch header carrying that "may be left empty" marker so the TLS preset's own legal word (`none`) is what goes out. The `summary` says which rung ran, in words, on the call where the HTTP tier ran. That referrer exists because some walls score a navigation with no referrer, so `off` is a decision that can make a previously-passing site fail: that is the rung doing what it says, and the sentence is there so the failure is traceable to it rather than to the site.

**Two of those settings are launch-level, and that is where they get applied **: canvas noise goes into the context's init script and the WebRTC policy into the browser's own startup arguments — neither can be changed under a running browser. So the shared warm browser is *built* at whichever rung is in force (`cred_defaults`, else `auto`) and every call that rides it gets that rung for real; changing the stored rung replaces the warm browser, which costs one cold start, exactly like changing `profile` does. A call asking for a rung the shared browser was not started with does not pretend to have got what it asked: it runs on its own browser and says so in the response notes, because what it gave up is not only the warm start but that browser's page state — logins included. `off` is the rung that lands there most often, which is another way of saying `off` is a decision and not a cheaper default. `basic` / `auto` / `aggressive` share the same launch identity, so they never pay it: the Cloudflare path and the resource budget are per-call settings. **A capture action on web_act asks for the same rung** through that tool's `anti_detect`, and there it means one thing: whether a Cloudflare challenge gets answered before the shutter (`off` / `basic` shoot the interstitial as-is, `auto` / `aggressive` answer it). The fingerprint half is that browser's launch fact, not this call's — so a capture that comes back with empty image boxes is fixed by storing a stronger rung, not by adding an argument to the screenshot. No rung ever asks a capture to drop images, styles or fonts: a blank frame is never what "screenshot this" meant.

## What the page is waiting for

**Stopped being a knob **: the browser tier extracts once the page has loaded, and pays a bounded 5s network-idle wait **only when it recognises that the page has not rendered** (its visible text is still ungrown while the page ships scripts). `wait` — a fixed sleep — is deleted with no replacement: nothing real is better served by sleeping a fixed number of milliseconds than by letting the page say when it is done, and a fixed sleep is exactly how an intermittent failure gets hidden. The settle is inside your `timeout` and visible in `duration_ms`, so a slow SPA costs what it costs and you can see it. `anti_detect` and `cdp_url` are the only two of the identity settings that stay per-call: the rung a wall needs and the browser a page belongs to are facts about the call in front of you, not about the machine. Waiting for a specific element is still expressible where it is the job — the `wait_selector` action in an `actions` chain.

The extraction path itself is not a knob: markdown / text / article / structured run through trafilatura's readability scoring first, markdownify when it comes back empty, and tag-stripping as the last resort — that ladder is walked for every call. `extraction_type` is the ordinary way to ask for `markdown` / `html` / `text` / `article` / `structured` and needs none of the above.

`extraction_type='check'` is the sixth value: a **changed-since-last-fetch receipt, not the page**. dhole re-reads the URL and answers whether it moved since dhole last stored it: `changed` true/false — a 304 Not Modified or a byte-identical body means false — with both sizes (`baseline_chars`/`fresh_chars`); when true, `first_divergence_at` (where the two versions part ways) and `diff_window` (fresh text around that spot; refetch with `markdown` to actually read the page). The anchor is dhole's own last html copy of that URL, kept 7 days; no comparable baseline yet → `changed=null` and this call fetched and recorded one, so ask again. One cheap call stands watch over a page you only re-read when it moves (the three receipt rows live in fields.md).

**A batch is `urls=[...]` with `extraction_type='check'`** (up to 10 rows): every URL keeps its own verdict, the top level adds `changed_urls` / `unchanged_urls` / `baseline_urls` / `error_urls` plus a `summary`, and one dead page becomes an error row instead of erasing its neighbours' verdicts. `actions=`, `schema=`, `nested_selector=` and `cdp_url=` are refused before any request — a check has no action chain, no field extraction and no attached-browser view. For a list that survives restarts and an exit code a scheduler can read, use `dhole watch` (`add` / `list` / `remove` / `run`; exit 0 none, 1 changed, 2 error). The first `run` records baselines; the second and later runs answer changed/unchanged.

## web_search: engines, ranking, dates

**Engine matrix** (10 keyless + 2 keyed; max 12 names per search). All 10 keyless
engines are in the default pool — there is no opt-in tier to name:

| Engine | Direct from CN | Notes |
|---|---|---|
| `baidu` / `bing` / `sogou` / `so360` (`360`) / `yandex` | ✔ | `sogou` and `so360` are both IP-rate-limited |
| `bing_global` / `brave` / `yahoo` | proxy needed | `yahoo` is a second entry into the Bing index (availability, not a new family) |
| `duckduckgo` (`ddg`) / `marginalia` | proxy needed | `duckduckgo` is Bing-family; `marginalia` is an independent small-web index |
| `tavily` / `bocha` | keyed (off by default) | **Per-call billing, quota deducted on dispatch** — only when the user names them |

Two search abilities are gone (their backends are retired): **WeChat-article
search** (`sogou_weixin` was the only index of that pool — weixin.sogou.com
content is not fully covered by the general engines) and **encyclopedia lookups as
structured answers** (`wikipedia` / `grokipedia` / `baidu_baike`; the general
engines still return those pages, they are just no longer queried as APIs).

**Vertical sources** (`sources=`): five keyless APIs beside the web pool —
`news` (GDELT DOC 2.0), `academic` (arXiv Atom), `qa` (Stack Exchange / Stack
Overflow), `code` (GitHub **repository** search, sorted by stars), `community`
(Hacker News via Algolia). `sources=['web','academic']` asks both; omitting
`'web'` asks only the verticals, and `engines=` is then refused because there is
no web pool to narrow. They are **not web index families**: a vertical row carries
an **empty** `engines_consensus` and never raises the `x of N` count, because
"arXiv agrees with arXiv" is not corroboration. `source` names the backend that
answered (`arxiv` / `gdelt` / `stackexchange` / `github` / `hackernews`), and
`source_detail` is one row per requested source:
`{source, backend, status, count, delivered, duration_ms, error?}` with `status`
in `ok|empty|blocked|timeout|error`. `count` is candidate rows left after the
site/date filters; `delivered` is how many are in this response — they differ
whenever ranking, the quality filters or `max_results` left that source out. A
source that was asked and answered with nothing still gets a row: "I asked and it
was empty" must not look like "I never asked". Vertical rows share the web rows'
reranker, `max_results` and quality filters; a URL present in both pools becomes
one row (the web row keeps its consensus and gains the backend name in `source`),
and two vertical rows with the same host + normalized title collapse to one.

**`sort='newest'`** orders only rows that state a publish **day**
(`published_precision='day'`) newest-first; month/year floors, relative stamps
and undated rows keep their relative order after every dated row, because a floor
is not a publish day. The summary reports **delivered** counts, not candidate
counts. On vertical sources the date window is applied **per row and exactly**
(not widened to an engine preset): `after=` drops older rows **and undated rows**
(they cannot be proven inside the window), while `before=` drops only provably
newer rows and keeps the undated. Dropped counts are named in the summary
(`vertical date window dropped N older than after= …`). The web pool still gets
`after=` only as the narrowest covering preset — `date_filter` reports that
separately.

**Vertical reliability**: GDELT is best-effort and rate-limits hard (one query per
5s; a 429 arrives as `status=blocked`, not as "no news"); unauthenticated GitHub
search allows 10 requests/min and says so on 403/429; arXiv and Stack Exchange are
stable but can be slow; Hacker News (Algolia) is the most reliable of the five.
One dead source never erases another's rows — each failure is its own report row
and the round still returns what answered.

**Ranking**: a local cross-encoder reranks. Two profiles are registered: `bge-zh` (default, bilingual, ~279MB, best Chinese) and `mmarco` (multilingual MiniLM int8, ~119MB, ~1.8x faster; same 67-query corpus P@5 0.552 vs 0.549, Chinese slightly lower, English higher). Choose with `DHOLE_RERANK_MODEL` — a startup read, so **restart the host to switch**; the response's `rerank_model` names the one that actually scored. While it is still loading in a fresh process, `rerank_mode=merge` gets the free path: rows are grouped by how many distinct query terms their title/snippet/URL carry (2+ first, then 1, then 0), and consensus + engine position order each group. Measured on the 67-query corpus (agent-a): merge P@5 0.370 -> 0.525, MRR 0.550 -> 0.731; the neural arm stays at 0.549 / 0.737. The grouping never runs when any row carries a model verdict — a synonym-only row the model called relevant is not demoted for missing literal words. One retry restores `neural`. `relevance_score` is normalized (top is always 1.0); `min_raw_relevance` is what can judge "the whole round is irrelevant" — the raw-score distribution is model-specific. For the default `bge-zh` (measured): off-topic ~1e-4, marginal ~0.2, true hits 0.93+. **Start at 0.1**; hard negatives on the same topic sit at p90 0.18, so higher starts killing good results. `fetch_hint` reports each round's raw-score span, and `rerank_model` tells you which calibration to use. `engines_consensus` counts independent index FAMILIES (7 total — `bing`, `bing_global`, `yahoo` and `duckduckgo` are one Bing-family entry, so 10 engines reach 7 families), not raw hits.

**Consensus-gated fan-out** (`fetch_content` + `fetch_min_consensus`): the auto-fetch set is where search's cheapest signal meets its most expensive step — consensus is already on every row and costs nothing extra, while each auto-fetched page is a real fetch plus its tokens. `fetch_min_consensus=N` (N ≥ 2) spends that budget only on hits corroborated by at least N independent index families, and names what it dropped in `consensus_skipped`. Three boundaries are load-bearing, because "fewer pages came back" must never be silent:

- **A floor of 1 is refused, not ignored.** Every result has at least one contributing family, so `fetch_min_consensus=1` would filter nothing — and a parameter that silently does nothing is the failure mode this tool avoids everywhere else. Same for `fetch_min_consensus ≥ 2` without `fetch_content=true`: the floor has nothing to gate, so the call is refused and says why.
- **When the pool returned one family, the floor is not applied.** `1 of 1 (no corroboration)` is not "nobody agreed" — it is "nobody *could* agree", because the pool was degraded or tiny. Reading that silence as disagreement would drop every result on a bad day. The summary says the floor was skipped and why.
- **When the floor removes every candidate, nothing is fetched — and it says so.** The floor was an explicit choice, so quietly falling back to "fetch them anyway" would do the opposite of what you asked. `consensus_skipped` lists them and the summary says nothing was fetched; `web_read` them by hand if you want them regardless.

The floor is off by default (0): `fetch_content=true` on its own behaves exactly as before. Every auto-fetched page carries its own `engines_consensus` whether or not the floor is set, so the fetched set can be judged without cross-referencing the result list.

**Dates**: dhole sends a date window to `bing` / `bing_global` / `brave` / `duckduckgo`
(keyed `bocha` / `tavily` too), and only as day/week/month/year presets — that list is the
table in code (`_DATE_AWARE_ENGINES`), and the per-round truth is `date_filter.engines_filtered`,
not this sentence. `after=<date>` is widened to the narrowest preset covering the window (`date_filter` reports what was sent and which engines got no date filter at all); `before=<date>` is a **per-row verdict, not a round-wide filter** — it is the upper bound of the window (`after=` is the lower one), so it keeps the rows published before that date and drops only the ones **provably newer** than it. Everything else stays: a row with no date, or one the engine wrote as "3 days ago" (relative), cannot be bounded against an absolute cutoff without pretending. `date_coverage` says exactly how many rows fell in each of those classes and how many were dropped, so a partial filter is never mistaken for a silent one. Not every engine puts a date on the page at all, and the ones that do put it on only some rows (measured on the frozen SERP corpus through the real parsers: sogou 4 of 8 rows, baidu 2 of 5 and 2 of 6, bing 4 of 4 on one layout and 1 of 4 on the other, bing_global 1 of 10 and that one relative, so360 and yandex none), so `published` is absent more often than you would like — read `date_coverage` before concluding the round was date-filtered. One engine's gap used to be dhole's own and is now closed: `baidu` is sent its time parameter (`gpc` / `stf`, an absolute range plus `stf_type=2`), pinned by payload differential — the key appears on the request that named a window and not on the one that sent no `timelimit`. Any engine outside that table answers with no date filter because **dhole sends it nothing**: that is a fact about this wire, so do not conclude an engine that received no filter cannot filter by date. Date-bounded increments belong to `feed_read(since=)`. There is **no `total_estimate`** — do not look for it, do not invent one.

**Parameters worth naming**: `max_results` (1–50, default 6) — the list is cheap, the fetches are not; raise it when snippets alone can answer, keep it low when every hit gets fetched. `exclude_sites` drops noisy domains from the pool — the mirror of `site=`. `region` is the engine region as given, folded into the cache key; omitted, it is derived from `location` + `language`. `fetch_schema` (`{properties: {...}}`) applies web_read's structured extraction to the pages auto-fetched by `fetch_content`, instead of their markdown — same shape rules, so one schema fills from search and fetch in one call. `mode='find_similar'` finds pages similar to a URL you already have (`url=`) — the one mode that runs with **no `query=`** (every other mode is refused without it, and a `query=` you do pass there is not what gets searched), so reach for it when a page is right and you want more like it, not when keywords failed.

**No SLA**: keyless engines are direct scrapes of public search results (unauthorized, unquota'd) — when providers change layout or ban IPs, they degrade **silently**. For reliability: a different egress (`DHOLE_SEARCH_PROXY`) or a keyed backend.

## web_discover: the map, and what it costs

- One call, URLs only: `pages_crawled=0` in the answer is the design, not a failure. Reading the picks is `web_read(urls=[...])`; a second `web_crawl` would rediscover what is already in hand. Every map is also held server-side (1h) under the returned `plan_id`, and when the cap or the deadline stops a link-walked map early the held plan is the **whole** map (`pages_discovered` rows: the ones this answer shipped first, then the ones never sent) — `next_resume_token` points at the first of those — hand it to `web_crawl(resume_token=...)` to fetch the plan without re-sending URLs (see web_crawl below)
- A map has two prices. `sitemap=true` asks for the site's own index — one request, the whole site, and each row can carry the `<lastmod>` the site published. Without it the map is grown by walking links, which costs one request per step and stops at `max_pages` (1-40). `'auto'` tries the index first, then walks
- robots.txt still decides eligibility: URLs already known to be disallowed are dropped before any request and counted in `robots_skipped`. A map is not a promise that those pages can be fetched
- Map rows carry only what differs from the default, because a map's length is set by the site rather than by the caller — a 1000-URL map is 70KB of URLs, and restating one constant per row turned that into 350KB
- **A map's size is the site's call, so two knobs on THIS tool bound it.** `max_total_chars` (1,000-200,000, default 60,000, `0` = no cap) prices the **serialized rows**, which is the only part a map has: content rows carry no body, so the same budget used to overdraw itself (measured: 1,000 rows = 116,173 chars against a 60,000 ask, and `truncated_by_total_chars` said nothing). When it bites, `pages_discovered` is the size of the MAP and `len(pages)` is the rows that shipped, `truncated_by_total_chars=true`, and the held-back rows are stored with the ones you got — `next_resume_token='<plan_id>:<rows shipped>'`. Pass that back to **`web_discover`** (`resume_token=`) for the next rows: it walks no network, ships URLs only, and the arithmetic is `rows 561-1000 of 1000`. `web_crawl` with the same token FETCHES those rows' content instead — the cursor is shared, the verb is not. `max_pages` bounds neither: it counts page fetches and a map page fetches none, which the reply says rather than leaving it to guesswork
- **Map rows are not in the sitemap's own order, and the reply says how much moved.** A site's `sitemap.xml` is a document-order index, and document order means "what the site listed first", not "which page you want". Measured on a 1,000-entry sitemap that listed 100 documents plus 900 locale copies of them: the shipped page was 626 rows of which **0 were the originals**, and the page the caller wanted was in the map but past the budget. So rows are ordered by the same scorer the link-walk uses (your `search` terms when you gave any, otherwise the content prior: docs/api up, login/cart down), and the 4th-and-later locale variant of a page is placed **behind** the whole map instead of eating budget — up to 3 variants of a page still ship up front, so a site whose real content lives in `/ja/` is not folded away. Reordering only: the demoted rows are still rows of the map (`pages_discovered` counts them), still in the plan, still reachable with the cursor. The summary carries the counts (`N of M moved`, `K locale variant(s) of P page(s) placed behind the 3 copies kept up front`, `the X row(s) that shipped cover Y of the map's Z distinct page(s)`), and a map with nothing to fold says nothing about folding
- **A map built from `sitemap.xml` is fetched with no credentials** — that one request (and the `robots.txt` read in front of it) goes out bare, unlike the pages a crawl fetches. So a site that serves its sitemap only to an authenticated caller reads here as "no sitemap found", and when `cred_defaults` holds a credential for that host the summary says so in the same breath. The levers that do work: `sitemap=false` (link-walk, and those page fetches carry it), or `web_read` the sitemap URL itself
- **`timeout=` is the map's clock, and an empty map says which of the two ran out.** A `sitemap=true` map is one request, so that request needs to answer inside this call's budget: `timeout=` (whole call, ms, default 25,000, 1-120000 or refused by name) bounds both the call and the index request, and `web_crawl`'s own clock is `deadline_ms`. It used to bound neither — the number was handed to the engine as a per-page budget while the map ran on `deadline_ms` and the index request on a hardcoded 15s, so measured against a site whose `/sitemap.xml` answers after 20s, `timeout=30000` and `timeout=120000` returned the same 30.0s wall clock, the same empty map, and the same sentence blaming the site. Now the reply distinguishes the two ways a map comes back empty: **"ran out this call's time budget … that is the clock this call was given, not a 'no' from the site"** (raise the knob `next_action` names — `timeout=` here, `deadline_ms` on `web_crawl`) versus the site answering with nothing to parse (change source: `sitemap=false`, or read the index URL directly). Retry the first one with the same budget and you get the same cut; that is why it names the number instead of saying "retry shortly"
- `path_include` / `path_exclude` scope the map exactly as they scope a crawl (`/docs` is a subtree, not a string prefix; the only wildcard is a trailing `/*`). `search` then filters it by keyword, and **what it can compare depends on how the map was made**: a link-walked map has URL + page title, while a `sitemap=true` map has only the `loc` the site published — so a word that lives in a page's title but not in its URL matches nothing there, and the summary names that half (leave `sitemap=` unset so the map is link-walked and each row's title gets read, or use `web_search`). Both filters run BEFORE the map's cap, so a keyword near the end of a 4,000-entry sitemap still arrives; filtering after the cap would return an empty map that reads as "this site has no such page". On a `resume_token` page they are honored the same way (they judge the URL text) and the summary counts what they kept

## web_crawl: discovery economics and politeness

- The map is its own tool: `web_discover` returns URLs without body extraction, but **expanding the link graph still costs one request per page** (up to `max_pages`). For a one-request map: `sitemap=true` (whole site) or `max_pages=1` (start page's links only)
- **A big site is a plan, not a parade of URLs**: `web_discover` holds its map server-side for 1h and returns a `plan_id`. `web_crawl(url=..., resume_token='<plan_id>:0')` fetches that plan WITHOUT re-sending the URL list — a 1000-page task costs O(1) arguments per round instead of ~7.6KB of re-typed URLs. When the page cap, the char budget or the deadline stops the run, the reply carries `next_resume_token`; pass it back (same selector=/schema=) to continue exactly where the budget bit — same plan + same token = the same pages, so nothing is refetched or skipped. `selector=` (CSS) and `schema=` (same shape as web_read's) project every planned page — without them the rows are plain markdown, the same shape a crawl returns. Tokens live 1h; an expired one is named as such and the fix is one fresh `web_discover`. After mapping, read a few picks directly with `web_read(urls=[...])` — one call, no re-discovery
- `focus='query'` does two different jobs at once: it **prioritizes the links** whose path and anchor text look relevant (the best-first queue scores them) and it **filters each fetched page** down to the blocks matching the query — the same trimming `web_read` does, applied per page. Passing `focus` therefore does not only narrow what you read, it changes which pages get reached at all; leave it out for an unbiased crawl. `search=` is narrower in one way and wider in another: it filters the URL map **without** touching the bodies (that is the job `focus` does), but it is also the query the map's rows are ordered by — the same scorer the link-walk uses, so passing it changes **which rows ship first**, not only which rows survive (see the map section: `N of M moved`). The map's own document order is never what ships: with `search=` the rows go by your terms, without it they go by the content prior (`docs`/`api` up, `login`/`cart` down), so `search=` changes *which* rows are early, not *whether* they are ordered
- `path_include` / `path_exclude` match **path subtrees**: `'/docs'` matches `/docs` and everything below it but NOT `/docs-old`; the only wildcard is a trailing `/*`. When a run stops early, the advice may point at one subtree to scope to — but only when a subtree is a **subset** of what is still queued. If every queued URL already sits under that one segment (which is what a `path_include` you passed does), scoping selects nothing, so the reply says so plainly instead of recommending it; the budget levers are the ones that still change the result
- `max_depth` (default 2, range 0–5) is hops from the start URL; `0` maps the start page alone — raise it when the pages sit deep behind menus, lower it when the front pages already link what you want
- Budget: three caps, and the summary names the one that bit. `max_pages` (1-40, default 10) × `max_content_chars_per` (500-20,000, default 8,000) say how much is FETCHED and how much of each page comes back; `max_total_chars` (default 60,000, max 200,000, `0` = no cap) says how much this call may RETURN — when it is spent the crawl stops before the next batch is fetched, and `truncation=total_chars` reports how many URLs were left in the queue (and how many were fetched inside the last batch but not returned). Whichever of the three bites, the URLs left in the queue are stored under `plan_id` and the reply hands back `next_resume_token='<plan_id>:0'` — `web_crawl(resume_token=...)` sends exactly that segment without re-fetching the pages this run already returned, which is the part a plain "raise the cap and re-run" pays twice. Which cap bites first depends on page weight: on dense pages (nearly-full 8k bodies) the whole-run cap bites before `max_pages`, on thin pages the page count does. A map run through this tool is priced the same way, on the **serialized rows** — see web_discover above.
- A resumed plan (`resume_token=`) fetches content, so the map predicates `search` / `path_include` / `path_exclude` are REFUSED there by name rather than carried along inert — they scope a map while it is walked, and a plan has already been walked. `discover_only=true` on the same token instead returns the next map rows (no network), which is where those three keys do work.
- The `deadline_ms` default (25,000) is sized to a 30s host MCP timeout — a call the host kills first returns nothing at all, so the crawl stops and returns what it has instead. On a host that allows longer calls, raise `deadline_ms` explicitly; big sitemaps want it
- Politeness: `concurrency` (requests in flight) is the only knob left. The interval between requests to one host comes from **that host's `robots.txt` `Crawl-delay`** — `delay=` is gone, because spacing someone else's server is not a performance choice and the site already stated its preference. The value used is named in `summary` (with its author), the robots layer clamps any ask to 60s, and `ignore_robots=true` waives it. Note Python's robotparser only reads whole seconds — `Crawl-delay: 0.5` counts as no request at all
- List pages return a **structured link listing** instead of body text (`page_type=list`) — intentional, not an extraction bug
- **Every page a crawl fetches carries the credential `cred_defaults` holds for that host**, and `identity_applied` on the envelope names (keys only) which of them actually ran. It is on the envelope and not on the rows because a crawl row is a trimmed page report — the per-page receipt would otherwise never reach you. Read it before treating a crawl as "what a visitor sees": a 20-page run on a host you have a token for is your logged view, twenty times
- robots.txt is honored page-by-page: links known to be disallowed are dropped before enqueueing
- With `focus_engine="neural"` and a `focus` query, each discovered page is scored against it before extraction deepens; pages below the off-topic floor (0.03) leave the queue and the count lands in `summary` (model missing = filter silently OFF — a crawl never fails for an optional enhancement; your named start URLs are never dropped). Default (no `focus_engine`, or `"bm25"`) skips the semantic scoring entirely — the cost is per page, so it multiplies by `max_pages`

## The remaining tools

**Screenshots ride web_act's action chain** (A1 absorbed the standalone tool): `{"screenshot": "css"}` crops one element and returns it inline; the dict form adds `decode_qr` (local QR decode), `full_page` (whole scrollable page, no selector), `image_type` (`png`|`jpeg`) with `quality` (jpeg only), and `save_to` — the capture writes to disk (parents created; a non-image file name is refused to protect it, same-named images may be overwritten) and the receipt reports the absolute path + byte size, keeping the bytes off the transcript. Inline captures cap at 2MB; `save_to` is the route around it. The capture runs on the SAME page instance as the surrounding actions — a captcha you crop is the one the next action answers.

**doc_parse**: the only entry point for local documents in an MCP-only client (no file tools of its own), and the only safe one anywhere for a zip/container format or a file whose encoding you don't know — a docx/xlsx/pptx/odt is a zip and a pdf is a container, so a text reader sees bytes, and a non-UTF-8 csv/html decodes into plausible-looking **wrong** text rather than an error. Extensions: .html/.htm/.xhtml/.docx/.xlsx/.xlsm/.csv/.tsv/.pdf/.md/.markdown/.txt/.json/.yaml/.yml/.pptx/.odt; .json/.yaml are **validated** (a broken file is one error line, not a byte dump); unlisted extensions (.log/.rst/.ini…) are refused with a rename-to-.txt hint. A pre-2007 Office file (.doc/.xls/.ppt) is **OLE2/CFB, not the zip this reader opens** — it is caught by its magic bytes and refused by name (naming the format it actually is, plus the `soffice --headless --convert-to` command that converts it), because the extension alone would route a `.doc` straight at the docx reader and fail with a generic zip error. That conversion target is named **only** for the seven extensions in that map; a CFB file that is not one of them (an `.msi`, a `.msg`) is refused with `there is no conversion target to name` — it is a package of streams, not text, so telling it to save as a document would be a second voice contradicting the first. Mojibake → explicit `encoding=`. PDF only: `pages=` narrows what is EXTRACTED (`'1-5'` / `'1,3,5-7'`) while the file is still downloaded whole, and `password=` opens an encrypted PDF — both spelled and described **identically** on `web_read`, so a range that works there works here. An argument with nothing to act on says so instead of disappearing: `pages=` / `password=` on any format other than .pdf are accepted and **not applied**, and the delivery then opens with one declared line — `> pages="1-2" did nothing here: .docx has no page concept (pages= slices .pdf only). What is below is the whole file, not a page range.` — because a silent ignore reads as "this document is only two pages long". Two shapes are locked: the line names the parameter, never its `password` **value** (a credential is not echoed), and it appears only where the argument truly did nothing — a .pdf where `pages=` sliced the body gets no such line, and a call that passed nothing gets no placeholder. The declaration costs the document nothing: remove that one line and the body is byte-identical to the same call made without the argument. A line that repeats at the same page edge (`running header` / `running footer`) is lifted out of the body and then quoted **verbatim once** in that first line, e.g. `> running header removed from the body: "…" (first line of pages 1-3; numbers vary page to page)` — journals print their masthead and their download watermark on every page, and anyone copying the body has been deleting them by hand per page. The test is shape only, never a keyword: the page's first-or-last **printed** line (measured on what the page prints, not on what paragraph-merging stitched together - a two-sentence paragraph the layout joined stays in the body, and one whose sentences differ only by a page number is the trap that used to make this delete real prose), one line, ≤120 characters, and the same line with **digits folded** (`[page 2 of 4]` and `[page 3 of 4]` are one line) on at least two pages of the same side. The same measured line that is **not** standing on its own (paragraph merging placed it inside a longer block) deletes nothing and says so, in a second sentence: `> last printed line repeats on pages 1-3 but stays in the body: "…"; numbers vary page to page - on those pages it sits inside a longer paragraph instead of standing as its own line, … Delete that line by hand if you want it gone.` It uses **position** words, not `running header` / `running footer`, deliberately: calling that line page furniture would be a verdict, and nothing here separates a printed page-edge line from the last line of a prose paragraph (measured on this repo's multi-page PDFs - repeating edge lines reach body font size, ratio 1.000, while a line printed on one page alone drops to 0.687, so the two piles overlap and any cut would start deleting real prose). A heading recognized by font size is named by neither sentence, a document whose edge lines do not repeat pays neither, and a page whose only text is that repeated line stays silent (that shape is "removing it would hand back a blank page", not "it was merged"). So: a page window narrows what is **delivered**, not what is **measured** — pages outside the window are read for their first and last line only (cheap text layer, no re-rendering), so `pages="2"` of a three-page journal still lifts the watermark and the note then names both sides of that fact: `(last line of pages 1-3; evidence from pages 1, 3 outside this window, delivered here: page 2)`. A document that really holds one page gets no claim (repetition needs two pages to measure), a repeated line in the middle of the page stays (that is structure, not page furniture), a long repeated line stays (deleting a real paragraph costs more than leaving a noise line), and a page whose only text is that line keeps it rather than being handed back blank. PDF **date** facts come in two labelled kinds and neither may pretend to be the other: the file's own stamps print on their own line as `> Created: … · Modified: … (the file's own stamps - when this PDF was written, not when the work was written)` — never a bare `Date:` that could be read either way — while the date shapes actually printed on the returned pages are counted and listed most-specific-first with the pages they sit on: `> dates readable in the returned text, most specific first: <full date> (page 1), <year-month> (pages 1-3), <year> (pages 1-3) - … no date here is a stated publication date for the work`. Nothing picks a publication year, because a creation date is when this file was exported and a masthead year is when a journal was copyrighted; the sentence names that rather than guessing. Shape again, not vocabulary: a 4-digit year (1800-2099), optionally `-MM`, optionally `-DD`, the longest shape winning each position so a full date never also yields its own bare year; more than 8 candidates are counted, not listed, because a reference list is not this document's date. A document with no date shape gets no line. A PDF's **title line** comes from the pages, not from the info dictionary: when the delivery ships a section map of its own (`table_of_contents`, measured from the file's bookmarks or from font sizes), the info-dictionary `Title` is file furniture of the same kind as `Author` / `Subject` / `Keywords`, and it prints inside that labeled `>` line as `Title: …` instead of heading the outline — because whoever produced the file may have left the field at its library's default (`untitled` arrives with `anonymous` and `unspecified` from one common writer), and a placeholder sitting on the top `#` rung reads as the document's title when it is only a field on the file. Three shapes follow from that: a document whose pages offer **no** outline keeps its `# <Title>`, because that field is then the only title there is and losing it would cost more than the misattribution; a Title string the pages print anyway appears **once**, in the outline, not also in the labeled line; and no Title field means no line. The pages' own heading is never moved, renamed or re-ranked by any of this. PDF file furniture arrives **grouped by who wrote it**: `Title` / `Author` / `Subject` / `Keywords` print as one line ending `(this file's own info dictionary - recorded by the app that wrote the file, not text printed on its pages)`, and the two stamps print on their own line with their own sentence — one clause at the end of a mixed line can only describe part of what sits on it, and `Author: anonymous` sharing a line with `Created:` reads as a timestamp instead of as a claim about who wrote the work. The attribution is uniform on purpose: no list of placeholder words decides which value is a default (one common writer hands out `anonymous` / `unspecified` when nobody filled the fields, and a genuinely anonymous work arrives with the same string), so the line says whose statement it is and leaves the judgement to the reader. A short numbered line that heads a paragraph (`2. Data`, `1.2.4 Sub-heading depth`) is split out of the prose it heads: some manuscripts print their section numbers at the body size with the body leading, which leaves the layout layer nothing to distinguish a heading from a sentence, and paragraph merging then handed back `2. Data Two Sentinel-2 tiles …` as one run of text. Shape again, never vocabulary: a 1-2 digit number (with optional dotted levels) opening the line, ≤60 characters total, and no sentence-ending punctuation at the end — so a wrapped line that happens to open with a year, a list item written as a full sentence, and an over-long numbered sentence all stay inside their paragraph. Splitting is all it does: the line is NOT promoted to `#` and is NOT added to `table_of_contents`, because a bare number line earns "this line stands alone", not "this is a level-2 heading". Parts a text tool cannot carry are declared in the **first line** of output, never silently dropped: pptx layout, odt styles and comments, and a docx's headers/footers, footnotes, comments and images (named only when the file actually holds them). A pptx's **speaker notes** do come through — under the slide they belong to, marked `> Notes:` — because a deck's body is often just headings while the script, the sources and the talking points live in the notes; they are labeled so they are never mistaken for slide content, and a slide without notes gets no placeholder. Layout fields (`<a:fld>`: slide number, date) are placeholders, not authored text, and are never emitted as content. A docx heading carries **the level the file declares** (`w:outlineLvl` — the field Word's navigation pane reads), not the display name of its style: a document whose style is named 标题 1 (Chinese Word's spelling of Heading 1) still comes out `#`, a custom style built on Heading 2 comes out `##` through its `basedOn` inheritance, a level written on the paragraph itself outranks the style's, and Word's levels 5 and 6 come out `#####` / `######` instead of dissolving into the body. Two collisions are said in the first line rather than flattened quietly: a document **title** is not part of the outline yet rides the same `#` as a level-1 heading (`its document title rides the same # rung as the file's 2 level-1 heading(s)`), and Word declares nine levels where markdown has six (`N deep heading(s) flattened to ######, markdown has no rung below that` names how many). A paragraph carrying `w:outlineLvl="9"` is Word's own spelling of "this line is body text", so it gets no `#` even when its style is named Heading 1. A document that needs neither note pays neither, and a package whose styles declare no levels at all falls back to the style-name mapping — fixing a wrong level never costs a heading. Two shapes worth knowing: a docx list keeps **the shape the file declares** — `w:numPr` on the paragraph or on its style (following `basedOn`) says "this line is a list item", and `word/numbering.xml` says which marker that level draws, so an ordered list arrives as `1.` items instead of bullets, `w:ilvl` becomes the item's indent (four spaces per nesting level), and a document whose style is named 列表段落 (Chinese Word's spelling of List Paragraph) loses nothing. `w:numId="0"` and `w:numFmt="none"` are Word's own spellings of "this line is not a list item", so they get no marker; a line that declares a list while its numbering part cannot be read keeps the bullet and does not claim a number; and a style that declares nothing still gets the shape its display name used to give it, because losing a list item is the worse misread. The other shape: a docx keeps its tables in **document order** (a table mid-document stays mid-document, so prose saying "see the table below" still points at it), and a sheet that hits the row cap says what it left behind — `N more row(s) not shown, of M in the sheet` — while a formula whose value was never cached comes back as its **formula text** instead of a blank cell. A sheet wider than the table on it is said in that same tail: `the grid is this sheet's used range, not one table's columns: 7 column(s) wide - 4 carry a title, 3 carry no header cell: E carries no value in any row; F holds a value only in row 2; G holds a value only in row 2 - no cell was moved or dropped`. openpyxl pads every row to the widest row on the sheet, so a summary pair parked two columns to the right of the table (columns F and G, on the sheet's second row) arrives as two extra fields glued onto the **first data row**, which reads as part of that record; the row numbers and column letters here are the sheet's own coordinates, the same ones you would type into Excel. Nothing is trimmed and nothing is moved, deliberately: an all-empty column is either the gap in front of an off-table summary or the ONLY separator between two side-by-side tables (A:C and E:F), so deleting it would glue two records together — a worse misread than the silence it replaces. A sheet whose every column carries a title gets no such sentence. Slides come out in the deck's own **play order**, and each section is headed by **where it sits** (`## Slide 2 of 5`), not by the part name it happens to have inside the package: the number in `slideN.xml` is a filename, not a position, so a deck someone reordered still reads in the order it plays, and nobody copying a slide's text into a handout has to delete a `.xml` first. The first line names where the order came from when it is not the deck's own list: `order taken from the file names, this package has no readable slide list`, or `the deck's own list named 3 of 9, the rest ordered by file name` — a heading that claims "slide 2" owes the reader the basis of that counting. A package whose slide list cannot be read falls back to filename order rather than dropping slides. HTML tables share one extraction function across parse / web_read / web_crawl — byte-identical markdown tables. `cwd` is the base directory for a relative `file_path` (absolute paths ignore it) — pass it when the host doesn't tell dhole the working directory. A path that resolves but names a **folder** is not a missing file: the answer is `Path is a directory, not a file: <the folder you passed> · doc_parse reads one file per call. Append one of these names to the directory you passed: a.docx, b.pdf, c.txt (3 file(s) at this level, 3 listed, 2 subdirector(ies) this call does not walk)`, and `next_action` says the path was FOUND so no amount of retrying with an absolute path or `cwd=` can change the answer — the old `File not found: … Pass an absolute path` sent folder-callers to re-check a spelling that was never wrong, and for an absolute path that sentence was self-refuting (the caller had already done the thing it asked). Three limits keep it honest: names are basenames of **this level only** (a tree is not walked, and the count of subdirectories says so), the list is capped at five with the real total named beside it, and a folder holding no regular file at this level says `it holds no regular file` instead of inventing a name. The machine root stays masked in the folder path exactly as in every other path answer; a genuinely missing file keeps its own sentence and its candidate list untouched — and that sentence now asks **which shape was passed**, once, where the shape is known: a `relative` name gets both doors (`Pass an absolute path, or pass cwd=<working directory> so relative paths resolve against it`), while a path that is **already absolute** gets neither, because `cwd=` is ignored for an absolute path by that argument's own schema and a way out that names an argument which cannot act on this call is a false door - what is left there is the name (spelling, extension, is it a file at all) and the place (name the directory plus the file inside it). The advice has one author: it is written in `error`, and `next_action` / `diagnosis.recover_with` send you there instead of restating it, because three copies of one sentence is three chances to contradict each other (measured before this: an already-absolute path was told to pass an absolute path, in three fields of the same receipt).

**feed_read**: batch RSS/Atom, newest first; item summaries are 500-char previews (`summary_truncated=true`) — fetch the item URL with web_read for full text. `since=` for incremental polls (ISO date or RFC-822 timestamp) — pass the newest `published` from the previous call; `items_older_than_since` counts what it dropped, and an entry whose date cannot be read is kept and counted as undated rather than silently dropped; passing a **site homepage** works — it follows the page's own alternate links to the feed (`discovered_from` records it); discovered addresses pass the SSRF guard too (a malicious page cannot weaponize auto-discovery against your intranet). Unparseable feeds fail with one plain-language verdict plus the candidates tried — don't re-parse XML yourself. The reply is an envelope like every other tool's: a top-level `summary` counts what happened (`N URLs asked · M rows answered · X rows carried Y items, newest first`, and when a source produced no row at all `asked` sits above `answered`), each row carries `fetched_at` - the instant that document arrived - and that field doubles as the answer to "is this a cached copy", because **`feed_read` holds no cache at all** (a stored feed would defeat its only purpose), so the fetch time and your call are the same event; a row with no `fetched_at` brought no document back. `next_action` shows up only when the whole batch delivered zero items, and it names which of the three reasons it was (all rows errored / a `since=` poll with nothing newer / sources that answered with nothing published) - a batch that shipped items pays no advice line. **A feed fetch sends no credentials**: `feed_read` is the one door that does not carry `cred_defaults`' `auth` / `cookies`, so what comes back is the public view of that address even on a host you have a token for — the row says exactly that in `note` when something is stored for it (`cred_defaults holds auth for this host and feed_read sent none of it`). For a feed behind a login, `web_read` that feed URL instead: it does carry the credential, and the XML arrives as content (item parsing is `feed_read`'s job, not `web_read`'s).

**Where a short link lands** (A2 retired `web_resolve`): `web_read` follows HTTP redirects and body meta-refresh, lands on the final page, and reports the hop — one call gives you both the destination and the content.

**sys_state**: one tool for what dhole keeps on this machine and how to erase a named class of it — the body cache (`cache.db`), the cookies a site left behind a `session_id=` (the session jar, in memory unless `DHOLE_PERSIST_CREDENTIALS=1`), the engine pool's cooldowns and yield history (`circuit_breaker.json` / `engine_stats.json`), and the stored default identity (in memory unless persisted).
- No arguments = **the census**: every open session with its hosts and cookie NAMES (a value is a credential; values never leave the process), how long before each one lapses, whether a browser is running under it, **what a `pin=true` call left in its hands** (`pinned_url` + `pinned_left_s`, the countdown on that page's reuse window — the same gate the next pinned call applies), plus the cache's entry/expiry counts. Reading is never an erasure. So "is the page I pinned still there when I get back?" is a question you can ASK, not one you learn from the call that finds it gone, and the three answers are three different shapes on the wire: **nothing pinned = both fields absent** (a page someone closed by hand reads that way too - the answer is "it is not there"); a `pinned_url` carrying `pinned_left_s: 0` = the window passed and dhole only releases that page when the next call looks at it; a `pinned_url` with `pinned_left_s: n` = n more seconds of standing on it. That 0 is a verdict, so it is never compacted away, while an absent countdown is not a zero - it is the absence of a page. The window counts from the LAST pinned call, not from the first: every call that stands on the page restarts it, so what you read is how long the NEXT call has, from now.
- `clear=` takes those class names, **or one open session id** to forget exactly that session.
- `clear=["cache"]` wipes the whole content cache and forgets robots verdicts with it (a site that just relaxed its rules should not stay refused until the TTL lapses). It leaves login state **alone** — forgetting cookies is the `sessions` class, a separate token, because it is a separate consequence. To refresh ONE url, pass `cache_ttl=0` to web_read/web_crawl instead of wiping the cache.
- `clear=["sessions"]` or `["all"]` **pause** without `confirm=true` and erase nothing. The rule behind that split is what you would notice: losing a site's cookies surfaces only at your next visit there. `cache` and `engine_state` need no confirm — their cost is the next call being slower or asking different engines.
- An unknown token is an error naming both the classes and the ids that ARE open, never a silent no-op — `clear=["cahce"]` that "succeeded" would be the worst possible answer.
- `show=["models"]` reports a class `clear=` cannot take: **the semantic reranker on this machine**. One verdict in `reranker.state` — `loaded` (this process holds the cross-encoder) / `on_disk` (its files are complete here, this process is not using them) / `not_downloaded` / `deps_absent` (the python extras are missing, so no model on disk could run) — plus `model` + `role` + `label` (which cross-encoder the registry points at), `raw_high`/`raw_med` (the tier lines this model mints), `present` and `files_here`/`files_expected`, `approx_mb`, and this process's own `load_attempts` / `last_attempt_ms` / `recorded_reason`. `available` lists **every registered profile** with `{model, role, label, languages, approx_mb, present, arch_supported, active}` — so you can see the fast profile before switching to it. Two of those deserve the reading: a **truncated download counts as not present** (that is why `files_here: 2` can sit next to `present: false`), and the ledger is what makes "installed but would not load" read differently from "installed and never tried here" — the same numbers `fetch_hint` quotes after its own sentence. No filesystem path appears here: this is machine-local state and tool output lands in the transcript. `dhole -v` asks the **same function** for the verdict, so the CLI and the wire cannot tell two stories about one model file. Erasing it is not a class dhole offers: `clear=["models"]` is refused with its own reason (not the `config` one — that door is `dhole config unset`), and a deleted model comes back on the first neural search that needs it, resumable.

**sys_state's `engine_state` class** is the MCP-side equivalent of `dhole engines reset`, and the one that reaches a server already running (the CLI clears the files; the process keeps its own copy in memory until it restarts).

## The stateful tool (cred_defaults)

Registered by default (no opt-in groups). If it is missing from `tools/list`, the operator named an explicit `DHOLE_TOOLS` subset — widening it is their call. The identity it stores lives in memory unless `DHOLE_PERSIST_CREDENTIALS=1` (then `~/.dhole/identity.db`, every value DPAPI-encrypted).

**cred_defaults — the identity later calls should assume.** Seven keys, one call: `proxy`, `profile`, `cdp`, `allow_private`, `anti_detect`, plus `auth` and `cookies`. The last two **require `"host"` in the same `set` object** and that is the tool's whole design: a stored credential with no host would ride along to the next site you read, which is a different site's request — the mistake the cross-origin credential drop prevents, made permanent. The match is dot-bounded (`api.example.com` takes a default stored for `example.com`; `evil-example.com` does not). The other five are global by nature: one egress, one browser context, one attached Chrome, one ladder, one private-host allowance.

Precedence is one rule with no exceptions: **what the caller passes this time beats what is stored, which beats the tool's own default.** Only two identity settings can be passed this time — `anti_detect` and `cdp_url` (see above for why those two). `auth` / `cookies` are stored per host, so "one site, different credential" is just another scoped row; `proxy` and `allow_private` are global, so reaching a single URL without them means `unset` around the call. `allow_private=false` is read as a decision rather than an absence. A stored proxy is credited as an explicit proxy (it gets the 5s TCP precheck and a dead one fails fast with `proxy_unreachable`); an environment proxy stays machine config and still decides nothing about one fetch, so a stored default is used in preference to it.

What comes back is **the redacted half**: `auth` as `{type, username}`, cookies as NAMES, a proxy as host + `credentials: true`. **Values never leave the process**: nothing the store holds is sent toward the transcript, and each later `web_read` response names what it ran on in `identity_applied`. `profile` is the named persistent browser context — the only way to name one — and changing it rotates the warm browser (one cold start) instead of silently keeping the old logins. `anti_detect` rotates it for the same reason: the rung's canvas and WebRTC settings are decided when that browser starts, so a stored rung that changed has to be launched to take effect (see the ladder above). Revocation: `unset=["proxy"]` forgets one key (every host scope of it), `sys_state(clear=["cred_defaults"])` forgets the whole store and needs no `confirm`, because a missing default shows up on the very next call.

## Local data and privacy (~/.dhole, relocatable via DHOLE_HOME)

| Location | Contents |
|---|---|
| `cache.db` | Fetched body text (plaintext SQLite), TTL 1h by default (article 6h) |
| `sessions.db` / `identity.db` | **Not created by default**: the cookie jar (24h expiry) and the stored identity hold credentials, so they stay in memory and end with the process. `DHOLE_PERSIST_CREDENTIALS=1` creates them — every value DPAPI-encrypted (bound to the Windows user; a copied file stays unreadable, a same-user process does not). A legacy plaintext file is absorbed into memory and deleted on first use, or re-encrypted in place in persist mode |
| `models/bge-zh/`、`models/mmarco/` | The rerank models — only the active profile is downloaded; copy the whole directory for offline reuse |
| `usage.jsonl` | With `DHOLE_USAGE_LOG=1`: call log (tool / duration / redacted errors) plus the audit channel — attach events, HTTP writes (non-GET), browser submits (names and outcome only, never parameter values) |

No telemetry: nothing leaves the process except traffic to the sites you point it at. Nuke `~/.dhole` for a full cleanup. Two legacy files that are no longer read: `search_proxies.json` (the proxy pool) still holds its credentials in plaintext, and `repair.py` is still a script that kills every dhole process and force-reinstalls if anyone runs it. Deleting the two files is the fix.
